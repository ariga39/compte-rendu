# Dashboard sign-in and review cancellation

Give an authorized operator a reliable way to stop a review. Roll out the increase from 30 to 90 minutes first so cancellation changes can receive a full review. The budget applies to automatically triggered and manually requested reviews, whether anyone has the dashboard open or not.

## What an operator sees

The shared header offers **Sign in with GitHub** on Overview, History, Help, Settings and job details. After sign-in it shows the account and **Sign out**. Return to the page that initiated sign-in, including a job permalink or supported list filters. Keep the return target in the state-bound OAuth flow. Reconstruct it from a recognized dashboard route and its supported query parameters; reject external origins, network paths and encoded path separators, cap its length, and fall back to Overview. Sign-out is a same-origin POST.

Anyone may still read the public dashboard. Signing in establishes identity. The existing per-instance numeric GitHub UID allowlist grants both editing model settings and cancelling runs. Retain its current configuration key for deployment compatibility and document the expanded authority. A signed-in account outside the list sees its account and sign-out, without operator controls. Reuse each instance’s GitHub App, encrypted host-only session, PKCE, state and expiry. Do not add a second login, new GitHub permission or 2FA check.

Keep public SSR, hydration and public API responses independent of personal state. The header gets viewer state from a private, no-store session endpoint after hydration through `GET /api/session`. Return signed-in identity and operator capability separately. Anonymous requests without a session cookie require no GitHub lookup. A GitHub outage must leave public browsing usable. On protected operations, the server resolves the GitHub user and checks the current allowlist again; a displayed button grants no authority. Logging out clears private client state.

A cancellable run shows **Cancel review** in its detail page and drawer. Confirmation identifies that run and explains that it will publish no review. Keep keyboard focus in the confirmation and return it to the detail view afterwards. Show **Cancelling** after acceptance, **Cancelled** when execution has stopped and cleanup is confirmed. Explain cleanup failure separately if intervention is needed. A refresh, closed tab or expired login after acceptance does not interrupt cancellation. History, filters, overview counts and the GitHub Check distinguish manual cancellation from failure and supersession. Preserve the existing privacy projection, including on private-repository rows. The operator's UID stays in the private audit record.

## One owner for cancellation and publication

Expose a same-origin authenticated `POST /api/jobs/:runId/cancel`. The public run ID identifies one immutable attempt. Core resolves its exact Runner job ID and attempt from D1; clients never supply a Runner ID. A session is required (401); a disallowed UID or wrong origin gets 403. Return 404 for an unknown run after authorization. Repeated requests return the current cancellation state without duplicating side effects.

| State when Core receives the request                     | Outcome                                                                                                                                                                                   |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Queued, no Runner claim                                  | Atomically finish as cancelled (200). A racing claim cannot take it. There is no Sandbox to clean up.                                                                                     |
| Claimed, publication unclaimed                           | Atomically set cancelled and record requester UID and timestamp (202 while cleanup is outstanding). Prevent new grants and publication for this attempt, and dispatch the stop to Runner. |
| Already cancelled, cleanup outstanding or complete       | Return 202 or 200 respectively. The job page can resume polling by run ID.                                                                                                                |
| Publication already claimed, or any other terminal state | Return 409 and refresh the detail. An existing GitHub review is never withdrawn by this action.                                                                                           |

The D1 conditional write for cancellation and the existing publication claim must exclude one another. A successful agent result alone does not win publication. After cancellation wins, a late success callback may record usage, evidence and cleanup for its exact attempt but cannot publish a review, change the verdict or turn cancellation into failure. Automatic supersession, retries and late callbacks must preserve the winning disposition. A new review of the same PR waits for confirmed cleanup of the previous Runner claim. No cancellation can target the replacement run.

Set the product disposition to cancelled in the same D1 write that accepts the request. End the GitHub Check on acceptance. For claimed runs the UI derives “Cancelling” from this disposition plus outstanding cleanup; failure to confirm destruction stays visible even after the Check ends. Preserve job ID and attempt for late evidence and usage; release the same-PR cleanup guard only on verified teardown. A cancellation callback bypasses publication, including the existing path that interprets a lost publication claim as completion. Allow a fresh manual retry after cleanup.

Migrate the status/disposition constraints on runs and deliveries while preserving existing rows, indexes and uniqueness rules. Include cancelled in cleanup recovery, queue blocking and dashboard filters/counts. The authenticated dashboard calls a Core operation with the verified UID; ingress does not expose a second unauthenticated control route. Update D1 constraints, claim and recovery queries, contracts and in-memory store together. Enforce the cancellation guard on check setup as well: if a Check is created in flight, reconcile its ID and end it with GitHub conclusion `cancelled` and manual-cancellation wording. The existing cancelled Check message specifically says a newer revision replaced the run. Keep previously dismissed reviews dismissed, and publish neither a failure comment nor an approval/change request for a cancelled run.

Reuse Runner’s authenticated `DELETE /jobs/:id` abort, grant revocation, Sandbox destruction and terminal callback. It can wait for teardown, so persist intent first and issue the stop independently of the browser response. Use the existing Worker scheduled path to retry a bounded set of outstanding stops and GitHub Check updates after delivery failures or Worker restarts. A Runner 404 can also mean the claim is in transit: retain the stop request. For a claimed job whose stop arrives before local admission, Core includes the same absolute claim deadline in the claim payload and authenticated stop request. For an unknown ID during a claim in flight, Runner retains the stop until that deadline or until the claim returns and is conclusively handled. Never extend the deadline on retry. Evict expired entries on lookup and on a deadline timer. When a stopped claim arrives, acknowledge the claim and send a cancelled callback with evidence that no Sandbox was created; do not halt the claim poller. Expired claims cannot start. Check cancellation again before starting the agent. Core also checks cancellation before authorizing inference. Bound each stop request independently of teardown. When the attempt and normal cleanup/recovery window elapse without proof, surface operator recovery and retain the same-PR blocker; do not retry an unknown job forever. An in-flight grant must still be revoked during cleanup. A matching callback or verified Runner terminal response can confirm teardown even if execution finished just before DELETE arrived. A lost response, a killed CLI client, or an unconfirmed Sandbox never counts as destruction. Keep unresolved cleanup visible and the same-PR guard in force through recovery. Preserve model usage incurred before cancellation.

## 90 minutes of review time

Set `REVIEW_ATTEMPT_BUDGET_MS` to 90 minutes. Use the durable Core claim timestamp as the start: time spent waiting in the queue is free; setup, all independent reviewers, synthesis and correction consume the same remaining budget. Pass the absolute deadline to Runner. Remove the agent-start clock reset and the agent command’s exception to remaining-time checks. Evidence collection, revocation, destruction and callback have bounded finalization time even when review time is exhausted. Signing out or session expiry does not affect a running job.

Core mints the fresh, single-repository GitHub read token after claiming. Send its validated expiry with the claim. Cap execution at the earlier of the claim deadline and credential expiry, reserving the existing safety margin for clock skew. A short-lived token cannot produce a run that looks active for an hour while GitHub reads have already expired. Test a read near the effective deadline and report which deadline ended execution. For sbx, Runner obtains a fresh read token through the authenticated Worker and replaces the current token before expiry. Core verifies the immutable claim identity, original deadline and publication ownership again before returning it. The other backends keep the initial credential cap. Core still obtains publication credentials separately.

Keep the existing four-times policy for relay grants (six hours after the change); normal completion and cancellation revoke them immediately. After a crash that prevents revocation, a stranded grant can remain valid for up to six hours. The browser login lifetime stays one hour. Runner requests a fixed two-hour OpenSandbox resource lifetime. The server must allow 7200 seconds to cover a 90-minute attempt plus teardown. Neither lifetime adds review time.

## Delivery and acceptance

1. **Shared sign-in.** Extract the existing authentication path, add header and private viewer state, preserve Settings authorization. Test anonymous SSR with GitHub unavailable, an allowed and disallowed user, direct job return, logout, expired sessions and rejected external return targets.
2. **Durable job control.** Implement the operator endpoint, state transitions, stop delivery and Check reconciliation. Exercise queued cancellation against claim, claimed cancellation against publication, retries after a dropped response, cleanup recovery, late success and a subsequent retry of the same PR. Verify exactly one outcome and no published review when cancellation wins.
3. **Operator controls.** Add confirmation, pending/terminal states and history in the detail views. Test both drawer and permalink, including reload while cancelling and an unauthorized direct POST. Verify an actual disposable review stops, its grant becomes unusable, its Sandbox is destroyed and its GitHub Check says cancelled.
4. **Increase the budget.** Deploy the timeout increase first. With controlled clocks verify a review can continue past 30 minutes and reaches timeout at the new boundary without resetting the budget. Check the actual runtime and credential limits, rollout documentation and rollback to 30 minutes. Drain Runners for binary replacement so running attempts finish under the version that admitted them.

The timeout rollout takes precedence over the numbered cancellation steps. Each step gets a separately reviewable PR. Approving this document authorizes implementation; runtime and production changes follow their own review and rollout.
