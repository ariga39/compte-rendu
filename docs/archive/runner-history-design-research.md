# Runner history and execution recovery (#307)

Initial design proposal, 2026-11-23. The implementation decision allows an interrupted review result to be lost. A fresh review must remain possible, and owned VM resources must be reclaimed automatically. The replay and acknowledgement proposals below record the alternatives considered during research.

Core stores the durable review record in D1. A Runner can discard a completed response once the system can answer historical queries, reconcile the result and establish safe replay behavior without that response. Those are three separate conditions.

## Proposed behavior

- **Read history.** Dashboard and operator history go through Core by run ID. The authenticated Runner GET serves active work and unresolved local obligations. Migrate consumers expecting a retired Runner response before changing the endpoint. Evidence contents remain in the existing archive.
- **Start work.** Production uses pull claims. D1 already assigns a job conditionally and can replay a prepared claim by request ID. Before any new external effect, distinguish receipt of a claim from an execution already started. Bind the attempt to its Runner and recover an ambiguous start from its ownership evidence. If the evidence is insufficient, hold that attempt for reconciliation. An expired deadline alone cannot establish destruction.
- **Direct submissions.** The current private POST accepts a submission without an absolute original deadline. Once its process-local identity is forgotten, an old copy could start another sandbox. Prefer retiring direct execution if caller inventory permits. If supported callers remain, migrate them to Core-owned admission and define replay semantics before deleting the identity store. Preserve identical repost and conflicting repost behavior during transition.
- **Stop and clean up.** Keep cancellation intent and review outcome in D1. Runner observes sandbox destruction. Core’s requestStop path treats 202 and 404 as unconfirmed and validates job, run, attempt and destruction on 200. Keep that property across eviction and restart. Record cleanup ownership before resource creation and clear it only when the relevant resources are verified absent.
- **Deliver results.** Retain the terminal callback for redelivery until Core durably settles that attempt. Repeated delivery after a lost acknowledgement must preserve the winner of a cancellation/completion race and must not publish another GitHub review. Separate releasing the delivery obligation from the configured retention of archived evidence.
- **Outage.** During a Core outage, existing authorized work remains subject to its original deadline. Local cleanup can proceed. Unacknowledged delivery or cleanup reports remain recoverable. New work requires a valid admission. If the Runner cannot record ownership safely, refuse that start before allocating resources.

## Migration and acceptance

Inventory direct clients, scripts and operational probes, including use of the retired GET and DELETE response. The dashboard already reads Core. Migrate any remaining external historical readers found by inventory. Establish replay-safe admission and recovery for each supported backend, then exercise delivery and stop reconciliation with Core offline and across process restarts. Remove terminal SQLite only once those consumers and guarantees have moved. The size limit explored in draft #374 can be evaluated independently as an interim mitigation if production pressure warrants it.

Verify through the public seams that an identical replay creates no second sandbox, a conflicting replay cannot steal the attempt, a delayed submission after restart cannot revive old work, losing a callback acknowledgement cannot duplicate publication, cancellation cannot claim destruction on a missing local job, and an interrupted create or cleanup can be reconciled against the exact owned resource. Include the crash window before the first evidence directory or callback exists.

## Alternatives and remaining decisions

Keeping #374 would preserve today's private API and bound stored response bodies with little migration work. Its database is process-scoped, so it cannot identify an attempt after a Runner restart. Keeping a durable local database is an option if recovery needs transactional updates across multiple local records. Start by testing whether existing per-job ownership records and callback evidence cover the required crash windows before introducing another store.

The production Core Runner client implements two DELETE operations. The dashboard GET reads Core. The Runner still implements direct POST and GET, and tests exercise them. External callers must be checked during migration. A private Runner returning 404 for a retired job can be safe for diagnostics, but Core must already hold the matching cleanup acknowledgement before it stops reconciling a cancelled job. An accepted callback replay and a successfully published GitHub review are also distinct outcomes.

## Independent design review

DeepSeek V4.1 Flash reviewed the proposal against the repository, its history, and upstream designs. The resulting recommendation is to retire the completed-job SQLite database and direct execution POST after checking private callers. Retain per-job records for outstanding execution, cleanup and delivery. Prefer extending existing ownership and callback files. A local database would warrant reconsideration if recovery needs a transaction across records.

Three changes from the initial proposal affect implementation order:

1. **Recover a claim before starting.** Core can prepare a response while the Runner holds its request ID only in memory. A restart between assignment and receipt can strand the claim and block later work on the same PR. Persist a recoverable request identity before polling, or use an equivalent pre-start handshake. Bind recovery to the assigned Runner. Before creating resources, persist the attempt and a backend-verifiable ownership identity. A repeated delivery must reconcile that record. Audit cancellation during claim replay so that an earlier ambiguous delivery cannot be reported as never started.
2. **Separate the two stop callers.** Today requestStop validates job, run, attempt and destruction; cancelJob accepts 202 as pending, throws on 404 and requires aborted plus destroyed on 200. A job can finish successfully just before the stop. Both paths should consume a compact observation matching the attempt and accept verified destruction for any terminal execution outcome. Core retains the cancellation or publication decision. A missing local job leaves cleanup unconfirmed.
3. **Release each obligation on its own evidence.** A final manifest alone leaves a crash window after resource creation and before finalization. Reuse each backend’s existing ownership proof where available. Verify recovery after create-before-ID-save and destroy-before-report for each backend. Keep the report until Core acknowledges the exact result or explicitly confirms it was already settled; a generic conflict or permanent rejection requires reconciliation. Discard the operational record after both delivery and destruction are settled. Evidence retention continues independently.

First verify outside callers; then establish restart-safe claim identity and resource ownership, align stop observations and acknowledge replayed callbacks. Finally remove the retired response store. Acceptance includes a lost claim response followed by Runner restart, a late stop after success, and a lost callback acknowledgement. Keep unresolved obligations recoverable under disk pressure by deferring new admission when ownership cannot be recorded. Never evict an unresolved obligation solely because it is old.
