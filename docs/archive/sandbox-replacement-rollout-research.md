# Replacing Docker sbx on sumire

Research update, 2026-11-22. The production backend is still sbx.

## What failed and what a replacement must improve

On henshin PR 45 the checkout succeeded, setting a sandbox secret failed, and every cleanup inventory operation returned “not signed in to Docker”. After device login, inspection by the retained job ID returned “not found”. Runner's authenticated cleanup recovery got HTTP 202, Core recorded destruction, and the next review of that PR was claimed. The service kept polling throughout. This establishes two separate dependencies: a working local runtime and Core's proof that the previous job released its resources. Removing the vendor login addresses the first failure. A local daemon outage can still produce the second. [Failed run](https://reviews.ariga39.dev/jobs/6c558bae-aace-441c-839e-de6249bed91e) · [Subsequent run](https://reviews.ariga39.dev/jobs/4320de08-e408-481d-a6d6-e9d7f7586aed)

Consider a Runner change independent of backend selection: suspend new claims on a confirmed runtime-wide unavailability signal, periodically probe readiness, and after recovery reconcile retained failed jobs by exact identity using the existing verification path. A missing sandbox is one input. Credential, grant, network policy and host cleanup checks still apply. A transient job-specific command error alone should not pause all work. [Existing operator procedure](../operations.md#recover-cleanup-after-an-authentication-failure)

## Two practical paths

**Least Runner implementation work: OpenSandbox 1.2.1 on ordinary Docker Engine.** An existing adapter ran the real CLI tools, checked out a public repo, used a GitHub read token through Vault and reached completed through Core and D1 with a fixture model and intercepted publication. The lifecycle worked with empty Docker client configuration. An explicit 80/443 egress restriction was needed. Plain containers share the host kernel. One server, Engine, workload and egress images require maintenance. On sumire the Runner user's shell could not find Docker CLI, the usual system/user Docker sockets were absent, docker.service was inactive, and K3s was active. The existing sbx installation does not fulfill the documented Engine prerequisites. [Native evidence](opensandbox-native-probe.md) · [Deployment requirements](../opensandbox.md)

Two implementation gaps matter before production cutover:

1. On deployed main, Runner enables read-token rotation only for sbx. An OpenSandbox run is capped by the original GitHub token's safe expiry even with a 90-minute claim budget. The pinned SDK has credentialVault.patch; the upstream documents the next flow seeing an acknowledged update. Wire rotation as a runtime capability and prove a subsequent GitHub request uses the replacement while the model binding still works. [Runner](https://github.com/ariga39/compte-rendu/blob/82af699/apps/runner/src/runner.ts) · [Vault patch semantics](https://github.com/opensandbox-group/OpenSandbox/blob/release-1.2.1/docs/guides/credential-vault.md)
2. Deployed maintenance recovery accepts only sbx callbacks. The OpenSandbox verifier is still in an open PR. Complete its timeout/resource-lifecycle review and verify recovery after loss of a delete acknowledgement against both the lifecycle API and local Engine inventory. [Recovery PR](https://github.com/ariga39/compte-rendu/pull/235)

**If fewer host services and hardware isolation take priority: compare an embedded local microVM against this working baseline.** Sumire is x86_64, 20 logical CPUs and 30 GiB RAM, and the Runner account has read/write access to /dev/kvm. Those are prerequisites; neither latency nor safe concurrency follows from them. Use the existing Ubuntu review image if supported, one disposable checkout, synthetic short-lived secrets and a fixture model. Compare a complete review, a credential rotation, a cancelled command and rediscovery of the exact resources after a Runner restart. Keep the production backend unchanged during those trials.

nono also runs on a Linux VPS with the required kernel isolation features. The earlier Debian 13 test used a host-loopback model endpoint. The follow-up below uses the topology of the current HTTPS relay. [Official nono release](https://github.com/nolabs-ai/nono/releases/tag/v0.82.0)

Gondolin also supplies local microVMs and host-side HTTP credential substitution. Its image builder currently targets Alpine, and network mediation supports HTTP/1.x. Porting the Ubuntu OpenCode/gh image and testing streamed requests would be additional work for this Runner. [Upstream limitations](https://github.com/earendil-works/gondolin/blob/ca98da589edd0cd1c79333c0a2229660bb43d37b/docs/limitations.md)

## Native follow-up on November 22

The trials used disposable Debian 13 VMs, synthetic credentials, a TLS model fixture in a separate network namespace, and a simulated GitHub API. The upstream model returned a fixed SSE review. Tests used OpenCode 2.0.32 and gh 2.98.0. No production job, credential, publication or upstream model was involved.

| Observation           | nono 0.82.0                                                                                                                                                                                                                                                                                                                                               | microsandbox 0.7.16                                                                                                                                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model request         | OpenCode received the expected review text through a credential reverse proxy with a remote HTTPS upstream.                                                                                                                                                                                                                                               | OpenCode received the expected review in the existing Ubuntu image. The guest used the runtime interception CA via Node's extra CA setting. Runner-side copy retrieved the JSONL and matched the expected text before removal.                       |
| Access to other ports | An unrelated host-loopback service was reachable from the supervisor and received zero direct or proxied requests from the sandbox. On the allowed relay hostname, however, the sandbox's ordinary HTTP request to a listening port 8443 received 200. Removing the two ordinary domain allow rules and keeping only credential routes gave the same 200. | With default-deny egress, gateway DNS and explicit TCP 443 rules for the model and GitHub hostnames, the supervisor got HTTP 200 on the relay's 8443 control while the guest connection failed. Credentialed HTTPS on 443 succeeded in that same VM. |
| GitHub token refresh  | A single supervised session ran gh before and after atomic replacement of a host-side test token. A trusted cmd credential source with a one-second test cache TTL returned the new value. The GitHub fixture identified generations one and two.                                                                                                         | The host rotated the GitHub secret with live modify. gh in the running VM reached the fixture with generation one and then generation two. The model credential still worked afterward.                                                              |
| Cancellation          | After the fixture observed an outstanding OpenCode request, terminating the supervised process group left zero matching OpenCode executable PIDs after one second (two before termination).                                                                                                                                                               | Forced removal during an outstanding OpenCode request terminated the attached execution, inspection reported the named sandbox absent, and the local inventory command succeeded.                                                                    |

Use **microsandbox for the next Runner adapter trial**. It preserved the port policy, used the existing OCI image, rotated the GitHub credential live, exported evidence and tore down an active job with its local tooling. For nono the open question has narrowed to enforcing the existing port boundary on forwarded HTTP traffic; replacing the model endpoint resolved the earlier host-loopback concern in the tested profile. The results cover normal teardown and explicit cancellation. Remaining acceptance work includes interrupted create/delete with a fresh Runner, parallel jobs, the final Runner/Core callback, and one canary review against a real model.
